# Load test baseline, 4 October 2026

Riipen Labs (Group 2) asked for "a program of testing" for problems that only
show up when many people use Autinerary at the same time. This is the first
run of that program: signed-out visitors only, up to 50 at once. Scripts and
how to repeat it are at the end.

## What we found

- **No errors at any level tested** (5, 10, 25 and 50 visitors at once,
  about 900 requests).
- **Pages and the API stay fast.** The landing and sign-up pages (served by
  Vercel's CDN) and the API's `/health` stay under 0.25 s at the 95th
  percentile at every level.
- **ResourceHub search is the first thing to slow down.** Its typical time
  (median) only goes from 0.3 s to 0.5 s, but the slowest 5% go from about
  0.5 s at 25 visitors to 2.1 to 2.5 s at 50. Search runs a database query
  (and, for typed searches, an embedding call) on every request, so it is the
  first place to look before a launch push. **Fixed the same day; see
  "After caching" below.**
- The slower 95th percentiles at 5 visitors (about 1.9 s for search) are cold
  starts: the first requests after a quiet period. They disappear at 10.

## Higher load (run the same evening)

**100 visitors at once.** The main app's pages answered 403 Forbidden to
about 90% of requests: Vercel's firewall blocked what looked like an attack,
because every request came from one machine at about 30 a second. Real
visitors come from many addresses, so this measures the firewall, not the
app; the block lifted within minutes. ResourceHub search had no errors and a
median of 0.08 s, but its slowest 5% rose to 2.7 to 2.9 s (0.22 s at 50
visitors). The test stopped itself before 200 visitors, as designed. A real
test above 50 needs load from several machines, or a firewall exception.

**5 people finishing setup at the same moment.** All 5 paths were made, in
48 to 72 s (median 59 s), about as long as one alone. But the API slowed for
everyone else meanwhile: a /health check took 0.21 s typically (0.09 s
before), 2.3 s for the slowest 5% and 4.8 s at worst. The AI calls are
already asynchronous, so the likely cause is the synchronous database calls
made during generation, on a small server. Next steps: profile one
generation, move synchronous database work off the request loop, and run a
second worker or a larger Render instance before a launch push.

## How to repeat it

From `backend/`:

```
python -m scripts.load_test browse                          # 5, 10, 25, 50 visitors, 20 s each
python -m scripts.load_test browse --stages 100,200         # higher levels
python -m scripts.load_test generate --users 5              # 5 path generations at once
python -m scripts.load_test browse --report ../docs/reports/load-test-YYYY-MM-DD.md
```

The browse test writes nothing and stops by itself after any stage where more
than 10% of requests fail. The generate test creates QA accounts named
`test.account+riipen-load-*@test.com`.

## After caching (same day, ResourceHub commit 999e58d)

Search now shares work that is the same for everyone (which venues match a
set of filters, with their ratings; a text query's semantic matches; matching
products) for 60 seconds per server instance, and identical searches that
arrive together share one database query. Distance from the person is still
worked out per request. The same change fixed rating and norm-score lookups
that failed outright for large result sets (one request carrying 712 venue
ids got HTTP 400; they are now sent 200 at a time).

Same test, same stages:

| ResourceHub search | 25 visitors, p95 | 50 visitors, p50 | 50 visitors, p95 |
|---|---:|---:|---:|
| By category, before | 0.71 s | 0.51 s | 2.14 s |
| By category, after | 0.17 s | 0.07 s | 0.22 s |
| By text, before | 0.54 s | 0.51 s | 2.49 s |
| By text, after | 0.17 s | 0.07 s | 0.34 s |

Still no errors at any level. The 5-visitor stage still shows cold starts
(p95 about 1.3 s), as before.

Found while testing, and fixed the same day (ResourceHub, after 999e58d):

- Search read at most 1,000 matching venues (the database's row limit) and
  applied condition, norm, life-area, rating and price filters after that, so
  a condition filter on its own saw about a tenth of the catalogue. Every
  filter now runs in the database and all matches are read, 1,000 at a time.
  The whole catalogue is now 9,542 venues instead of 1,000; parks 3,202
  instead of 1,000; condition "autism" 4 instead of 0; life area "workplace"
  39 instead of 5. The slowest first search (the whole catalogue, nothing
  cached) takes about 2 s; repeats about 0.03 s.
- Text search matched the whole phrase. Each word now has to appear
  somewhere, in any order ("autism support group": 2 venues instead of 0),
  falling back to any of the words when no venue has all of them.
